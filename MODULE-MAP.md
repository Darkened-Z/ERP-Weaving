# Module & Page Changes Map

Single reference for the **deliberate, mill-specific customizations** on each page/module.
Read this before touching a page so nothing already built gets reversed. When you change
a page, update its entry here.

Conventions: quality is keyed by grey-construction **CODE** (e.g. `GC-001`) everywhere.
Client-facing summaries are Roman Urdu; the freelancer works in English. Deploy = push to
`main` (Vercel auto-deploys). No AI markers in commits/repo.

## Yarn — External Purchase / Sale (`external/yarn/purchase`, `external/yarn/sale`) — BATCHES
- **Party is mandatory on both purchase and sale (owner 2026-10-18):** the Party Combobox is `required` (browser stops the save) and the save action refuses (`error=no_party`, "Nothing was saved") unless the party is a level-5 chart account — a partyless voucher used to save and silently never reach the ledger (YPV-0025, YSV-0022).
- **YSV posting = sale + purchase cost (owner 2026-10-18):** DR party / CR Income Yarn (5.01.01.01.0005) = Σ line amt, then **DR Income Yarn / CR Yarn Stock (`YARN_PURCHASE_STOCK`, 1.01.25.01.0001) = Σ lbs × the line batch's purchase rate** (`ext_yarn_pur_voucher_line.rate` by `batch_no`; narration "… (PURCHASE COST)"). Income Yarn = profit; Yarn Stock relieved of what YPV put in. A line whose batch has no rate carries no cost leg. Built once in `ysvDetails(vno)` for both the insert and update paths. A voucher with no party does not post at all (YSV-0022 on 2026-10-17 has none).
- **Every purchase line IS a batch.** `ext_yarn_pur_voucher_line.batch_no`, numbered `YPV-0001/A`, `/B`… (same than-serial convention as `IDP-0001/A`). The number is carried on the form in a hidden `line_batch_no`: saving deletes and re-inserts all lines, so without it a batch would be reassigned by position and any sale pointing at it would point at other yarn.
- **Sale picks a batch, not a count.** The `line_stock_key` datalist lists open batches as `YPV-0002/A · 21 (PV 90;10) Aj — bal x bag / y lbs @ rate — <godown>`; picking one fills count, blend, pack, **rate, brand and godown** from that purchase and writes `ext_yarn_sal_voucher_line.batch_no`. Uses `RowAutoFill … force` (the only place `force` is on) — re-picking a batch MUST re-derive rate/brand, else one batch sells at another's price.
- **Clearing a sale line's Stock Batch (✕) clears the whole line** (`clearRowOnEmpty`) and the save reads the batch from `line_stock_key`, not the hidden `line_batch_no` (2026-10, YSV #8): the ✕ used to clear only the picker, so qty/rate and the stale hidden batch re-saved the "deleted" line.
- **Balance is derived**: batch purchased qty − Σ sale lines on that batch, excluding the voucher being edited so it doesn't self-deduct. Nothing is stored.
- **The purchase line locks because a sale row exists** — never a stored flag. Padlock + amber row + "sold on YSV-000x", inputs read-only, erase ✕ removed. Delete or shrink the sale and the lock lifts by itself; no flag can strand yarn in stock.
- **Release valve** = the sale voucher's own **Edit/Final** (`ext_yarn_sal_voucher.lock_state`, mirrors `intGreyDespatch.lockState`). While every sale holding a batch is in EDIT the purchase line opens, showing a green "YSV-000x in edit".
- **Oversell guard is unconditional** (server, before the transaction): a batch with sales cannot be dropped from its purchase voucher or cut below what went out — `error=batch_sold&why=removed|short`. EDIT unlocks fields; it does NOT license overselling. This is what keeps a count from going negative at monthly clearance.
- **Godown**: `YARN_STOCK_GODOWN = 1.01.25.01.0001` pinned in code. Purchase auto-fills it and it stays changeable (F9); **sale's despatch party is read-only** — it comes from the batch. **Unit column dropped** on both (still submitted as hidden so existing rows keep their value).

## Finance — Advance Cheque (`finance/advance-cheque`)
- Advance-cheque lifecycle register. **VTYPE `ADV`**, phase in `trans_main.trnType` = `ISSUE` / `CLEAR` / `BOUNCE`. Each phase = one balanced 2-line voucher; status derived by grouping ADV vouchers on `chqNo` (BOUNCE→bounced, else CLEAR→cleared, else issued).
- **Issue is a multi-line grid** (`issueCheques`): each row = one cheque (party / bank-advance / chq no / date / amount / narration) → posts **one ISSUE voucher per party holding one cheque leg per row**; clear/bounce name the cheque (`?chq=`) and reverse only that leg, so each cheque is still its own lifecycle unit. Issues post under the FY of their date; clear/bounce stay in the issue's FY (the register pairs by vno within it). Delete removes only the clears/bounces between this issue and the next re-issue of the same number. Batch validates all rows, dedupes cheque numbers within-batch + against existing ADV issues. Row pickers = datalists (`adv-party-accts` all L≥4, `adv-adv-accts` = `1.01.15.03.*`); `RowAutoFill` fills the title columns.
- **Issue:** Dr Party (`accCode`) / Cr Bank-Advance. Party = any L≥4 acct; Bank-Advance picker filtered to `1.01.15.03.*` (per-bank advance sub-accts). **Cheque No re-usable after BOUNCE** — the dup check compares distinct ISSUE vs BOUNCE vouchers per chqNo (an active/cleared issue still blocks); clear/bounce guards use the same tallies; the register pairs issues↔bounces by vno order so a re-issued number shows ISSUED again (`cheque-register.ts` same rule).
- **Cash with cheque:** each issue line has a **Cash Amt** column — one voucher then posts Dr party (chq+cash) / Cr bank-advance (chq, carries chqNo) / Cr CASH account (cash, NO chqNo, srno 3). Cash acct resolved like CP (descShort `CASH` → desc contains CASH IN HAND → CASH). Lifecycle (clear/bounce) reverses ONLY the advance leg (`loadIssue.amount` = the chqNo-carrying credit). Register lists Chq Amount · Cash · Total.

## Finance — Cheque Books (`finance/cheque-books`)
- Cheque-book master + cheque dashboard (modelled on the client's reference). Tables **`cheque_books`** (name unique, bankAcc, accountNo, prefix, startNo, leaves, status, createdAt) + **`cheque_status`** (chqNo unique, status, note, updatedAt — manual STOPPED/CANCELED/MISSED override). Both created in Turso via raw DDL (additive; `drizzle-kit push` sees no diff).
- Register lives in **`src/lib/cheque-register.ts`** (`loadChequeRegister(descMap)`) — shared by dashboard + print. Outgoing cheques only (ADV/BP/CP); one entry per cheque no from its "origin" line (never the ADV CLEAR/BOUNCE reversal). `derived`: ADV bounce→Returned, ADV clear→Cleared, else Issued. `eff` = derived, but a manual override (Stopped/Canceled/Missed) replaces it **only while derived is Issued** (GL clear/bounce always wins).
- **Dashboard**: 8 counters (Issued/Cleared/Returned/Stopped/Canceled/Missed/Unused/Total), **Upcoming** (eff Issued, chqDate ≥ today) + **Past Due** (< today), and **Flagged & Undated** (manual-status or no-date). Each cheque row has an inline **Change** select (Issued/Stopped/Canceled/Missed → `setChequeStatus`; Issued clears the override).
- **Per-book usage**: leaf n = `startNo..startNo+leaves-1`; "used" if `prefix+n` or bare `n` matches a register cheque no. Usage bar + status tally + Unused. CRUD (create/edit; ADMIN delete); dup name → `error=exists`. **Print** = `finance/cheque-books/[id]/print` (full leaf register, standalone printable, PrintButton).
- Nav: Finance → Cheque Books (`fin-cheque-books`), next to Advance Cheque.
- **Clear:** Dr Bank-Advance / Cr Bank (`1.01.15.02.*`). **Bounce:** Dr Bank-Advance / Cr party dishonour (`1.01.15.04.*` "CHQ FAILLED <party>"). Both guard against double-processing (already cleared/bounced).
- **Re-issue** (on a bounced cheque): opens an ISSUE form prefilled with party + bank-advance + amount **and the bounced cheque's own number and date** — a bounced cheque physically comes back, so the same leaf is normally re-presented, and the issue guard already allows it (a number is free once bounces >= issues). Both are overtypeable for a new leaf. Leaving the no blank was why operators invented `1122/1`. (GL = normal issue; whether to also move dishonour→advance is an owner call — left as plain re-issue.)
- Delete (ADMIN) removes the issue + its clear/bounce (all vnos sharing the chq no). **Blocked once any cheque on the voucher has CLEARED** (owner 2026-10): Del is a locked button on every row of that voucher and the server refuses `error=cleared_no_delete` — same rule as Edit (`settled_no_edit`). Bounced-only vouchers can still be deleted.
- **Not Clear** (ADMIN, owner 2026-10): on a CLEARED cheque row — deletes that cheque's CLEAR voucher (Dr bank-advance / Cr bank or cash) so the cheque is ISSUED again; then Clear / Edit / Del work normally. Only the clear of that issue is removed (the CLEAR after it, before the next ISSUE of the same number); period lock applies to the clear's date. Postings flow into `/ledger` + `/reports/cheque-status` like other cheque vouchers. Reuses `getSession`, `assertPeriodOpen`, `Combobox`, `ConfirmButton` — same pattern as BP.

## Inventory — Knotting / Maroori / Sarning Bill (`inventory/knotting`)
- The loom-mount operation: pick a LOADED beam + a loom → on **Save** the beam mounts (beam `beams.statusWrk` **LOADED→KNOTTING** with loomNo/shed/knVno; loom `looms.statusWrk`→RUNNING + currentBeam). Edit reverses old lines (beam→LOADED, loom→S) then re-mounts current lines. Delete also reverses. VTYPE `KB` GL: DR expense (`KNOTTING_EXP`/`SARNING_EXP`/`MAROORI_EXP` by Type) / CR party.
- **Beam lifecycle**: LOADED (warped-beam receiving) → **KNOTTING** (this bill) → **PRODUCTION** (daily production applies it on save; legacy RUNNING treated as mounted too). Statuses seeded via `migrate-beam-status-flow.mjs` (run against Turso for prod).
- **Beam-status guard (IWB side)**: warped-beam save/edit/delete **never downgrades a beam that has advanced** past receiving (KNOTTING / PRODUCTION / RUNNING stay untouched — only receiving stamps + set/ends/length refresh). Previously editing an IWB voucher re-forced LOADED and silently broke the knotting mount (beams vanished from Daily Production). The IWB grid's Beam Status cell shows the beam's **LIVE** status, not the stale line value.
- **Beam lifecycle is ONE rule across the three pages (2026-09, owner): receiving → knotting → production must agree.** A beam is *on a loom* from the moment knotting mounts it until production empties it — that is every status except **EMPTY** (freed) and **LOADED** (received, never knotted), so `MOUNTED` = KNOTTING, PRODUCTION + all `BEAM_STATUS_CHOICES` (RUNNING, F-ROLL, L-ROLL, R-CUT, RE-KNOT). It used to be only KNOTTING/PRODUCTION/RUNNING, so a beam the operator set to **L-ROLL vanished from the beam picker and the loom fill mid-run**. Knotting's loom guard uses the same rule (`loom_no` set AND status ≠ EMPTY).
- **Loom lookup never crosses sheds:** loom numbers repeat per shed, so `beamsForLoom` keys on `shed|loomNo`. The loomNo-only fallback covers ONLY legacy beams with no shed stamp — it used to kick in whenever the scoped lookup was empty, so an emptied Shed 1 Loom 7 offered Shed 2 Loom 7's beam.
- **L-ROLL = last roll = beam finished (2026-09, owner).** Saving a production row with beam status **L-ROLL** empties the beam (`EMPTY`, `loomNo` null) AND frees the loom, exactly like picking EMPTY — the operator marks L-ROLL to say the beam is done. F-ROLL / R-CUT / RE-KNOT are mid-run and keep it mounted.
- **Last roll frees the LOOM, not just the beam:** when Σ woven ≥ beam length, daily production sets the beam EMPTY + `loomNo` null **and** clears `looms.statusWrk/currentBeam/currentContract`. Without that the loom kept pointing at an exhausted beam and never read as available for the next knotting.
- **Beam-status guard (DP side)**: DP **delete and edit-drop** release their beams back to the knotting mount — a beam carrying `knVno` goes back to **KNOTTING** (mount survives), only never-knotted beams revert to EMPTY. (Deleting a production voucher used to force EMPTY and silently un-mount knotted beams — the same regression class fixed on the IWB side.) The auto "last roll → EMPTY" when Σ woven ≥ beam length is intentional and stays.
- **ONE derivation for beam + loom state: `recomputeBeamStatus` (`src/lib/beam-cycle.ts`, 2026-10).** Every DP save/edit/delete calls it per beam; nothing else on the DP page writes beam/loom state. It (1) **re-stamps Rcvd/Mtr / Diff / Shrinkage** on every row of the cycle as a running Σ(total+rej) in **entry order (production id)** — editing an older voucher used to stamp it with the newest total + its own meters, so it outranked the later L-ROLL and put a finished beam back on its loom (AJ-6 took Shed 3 Loom 24 from AJ-1); (2) status = **last-entered row** (a wrong date can't reorder it); Σ woven ≥ beam length → EMPTY lives here too, so a later edit can't resurrect an exhausted beam; (3) no production yet → **KNOTTING only if the beam's knotting bill still has a line for it and `knDate ≥ brDate`**, else LOADED/EMPTY (a stale `knVno` left beams "KNOTTING" with no loom — invisible everywhere); (4) going back on a loom **never takes it from another mounted beam** → `LoomTakenError` → DP shows `loom_taken`. A re-mounted beam's stale L-ROLL/R-CUT `statusLoc` is reset to RUNNING.
- **R-CUT keeps the full beam length** (it used to shrink `beams.length` to the diff while Rcvd/Mtr stayed cumulative → double-counted, auto-emptied early). Remaining = length − Rcvd/Mtr.
- **Beams master (`weaving/beams`) decides "done" from Status Wrk only** — a stale L-ROLL in Status Loc used to empty a running beam on save.
- **Party** = knotting-contract party (Combobox from `intKnottingContract` status=R); `AutoFill` fills Rate Per Ends / Rate Per Beam / Type from the contract.
- **Shd# column REMOVED (2026-09, owner):** the beam pick used to stamp `shd_hash` from the beam, so a line could carry a shed with NO loom — which is how beams ended up sitting on "Shed 1" unmounted and invisible to daily production's loom-scoped beam picker. `shd_hash` survives as a hidden field; the loom value (`shed|loomNo`) is now the only thing that sets shed AND loom. The Lm# picker reads **"Shed 1 — Loom 24"** (`code`/`description` swapped for legibility) and is `min-w-[150px]` so the text is never clipped.
- **Shed comes from the Lm# pick, never the hidden `shd_hash` (2026-10):** the save used to prefer the hidden field, which only auto-filled while empty — re-picking "Shed 2 · Loom 14" after "Shed 3 · Loom 14" saved Shed 3 and mounted the beam on the wrong loom (IKS-0038 / AJ-15-340; daily production then found no beam on Shed 2 Loom 14). Server now takes the shed from the `shed|loomNo` value; the RowAutoFill is `force`. Daily production's header Loom# shed likewise beats the hidden Shed No on edit.
- **One loom, one beam (2026-09, owner):** a loom is occupied from the moment knotting mounts a beam onto it until production posts the **L-ROLL** on that beam — the LOV must not offer it in between. Occupancy is read from three places because any one can be missing on older rows: `beams.loom_no + status_wrk != EMPTY`, `looms.current_beam`, and any saved knotting line whose beam has not gone EMPTY. Exemption is per LINE (not per bill) — each row keeps its own current loom in its own picker so editing never loses it, and a bill-wide exemption used to let a second row re-pick the loom row 1 already held. Save re-guards it: `error=loom_dup` (two lines share a loom), `error=loom_busy` (loom carries another beam or `looms.current_beam` is set). Regression it fixes: pre-2026-09 knotting a second beam onto an occupied loom silently overwrote the mount (AJ-1 and AJ-10 both on shed 1 loom 7).
- **Line-item pickers** (both `FindingPicker` LOVs, `RowAutoFill` fills siblings):
  - **Beam # (F9)** = "SET NO LIST" of LOADED beams (`beams` where statusWrk=LOADED); columns Beam No/Set No/Beam Set/Status/Length/Ends/GP(brVno). Pick → fills `beam_set_no`, `set_no`, `beam_length`, `ends`, `beam_status` (readonly col). `beamFillMap` keyed by beamNo.
  - **Lm# (F9)** = LOOM LIST (`looms`, ordered by shed); value **`shed|loomNo`** (loom numbers repeat across sheds — same convention now in Daily Production), columns Shed/Loom/RPM/Status. Pick → fills `shd_hash` (readonly). Save splits `shed|loomNo`.
- **Live Amount + Total** via `src/components/knotting-calc.tsx` (`KnottingCalc`): amount = ends × ratePerEnds (else ratePerBeam per active row), net = amount + ext amt, running Total in `#ks-total`. Server recomputes the same on save (grid amount/net are display).
- **Empty-row guard**: a line saves only if it has beam/set/loom/ends/amount — `issue_date`/`k_date`/`shd_hash` (auto-defaults) alone no longer create blank lines.

## Inventory — Grey Cloth Despatch (`inventory/grey-despatch`) — thaans panel + line grid

- **The route lists UNDELIVERED thans, so a saved voucher's own thans must be asked for by name.** Saving stamps `dlv_status='Y'`; without the `keep=` query param (comma-separated mm/Than Sr No) reopening IGD-0001 showed an empty panel and no trace of the 200 m it carried. `seeded` ref gates `fillLineGrid` so the first render of an edit cannot wipe the server-rendered hidden line inputs with an empty selection.
- **`l_no` IS the GL voucher number.** The field defaulted to `MAX(l_no)`, which is 0 on the first despatch ever, and the ledger post is guarded on `vno > 0` — IGD-0001 saved with **no GL entry at all**. New vouchers take `MAX+1`, a submitted `0` never wins over the next free number, and an existing `0` is handed a real number on its next save. Keep it that way.
- **Scoped to the CONTRACT, not the party (2026-09, owner):** `thans/route.ts` filters on `int_daily_production_set.cont_no = <contract>`. It used to resolve the contract's party and list that whole party's thans — a party runs several contracts and a than's QUALITY follows its contract, so the list mixed qualities with no way to tell them apart. For that to work `cont_no` must actually be stamped: beams carry no contract in practice, so daily production's `saveAction` falls back to the header's picked `conv_contract` for any row whose beam gave none. Existing rows were backfilled.
- **PRODUCTION THAANS panel** (`DesignThansFill` in `production-calc.tsx`, data from `inventory/grey-despatch/thans/route.ts`): seeded on mount from the saved voucher (`savedContNo` + `savedThans`) and thereafter by a `combobox:change` on **`conv_cont_no`** — the route resolves the contract's party (int then ext table) and lists that party's undelivered thans. Picking/unpicking rows drives the line grid below via `fillLineGrid`.
- **Rows are keyed by `int_daily_production_set.id`, never by the serial (2026-09).** One production voucher's thans **share one `mm_than_sr_no`** (the grade tag is per row, not per than), so a serial-keyed `removed` set deleted both rows of a voucher at once and React saw duplicate keys. The route returns `id` for exactly this.
- **Beam#/Set# fallback:** daily production pairs a counts row with the beam row at the SAME index, so the 2nd, 3rd … than of a single-beam voucher is stored with `beam_no` NULL. The route fills those in from the voucher's beam **only when the voucher ran on exactly one beam** — multi-beam vouchers keep the blank rather than guess.
- **The panel IS the line list (owner):** the separate editable line grid was REMOVED — it repeated the same thans. The panel now renders in its place (left column), and `line_t_sr_/a_/b_/c_/cp_/rej_/len_${i}` survive as **hidden inputs** that `fillLineGrid` writes and `saveAction` still reads, so every line/than-consumption/GL path is untouched. Manual typing of a than is gone with the grid.
- **Right column order (owner): Party FIRST**, then Despatch To / Despatch Location, then Conv.Cont No, then Despatch From / Type. Party leads because it scopes the contract list. **Post Lot No and Shed No removed** from the form — kept as hidden inputs so a saved voucher keeps its values through an edit.
- **Lower block trimmed (owner):** F.T Weave, L.B/Mtr, Brk Code, Supervisor, Brkg Per Mtr, %age, Comm, Loom Type, Bill No/Date/Status are OFF the form — all kept as hidden inputs so a saved voucher keeps them through an edit; DB columns untouched. What stays: Product Brand, Blend, Gray Code, Width, Remarks.
- **Conv.Cont No is an Oracle-style `FindingPicker`** (title `CONV. CONT LIST`), not a combobox: columns **Cont No · Product Name · Product Coding · Conv Rate · Grey Rate · Cont Date**, `filterByField="party"`, running contracts only. A than is picked by QUALITY, so the list must show the product and its construction on its face.
- **Party = the WVG conversion party** (`1.01.01.01.*`, same head as daily production's Yarn Cost Party) — it used to list every level-5 account (400+). Zero despatches existed when this narrowed, so nothing was orphaned.
- **Totals:** the panel header and its tfoot show the selected than count and Σ meters. **Than / Qty and Qty Mtrs are readonly and auto-filled** from the grid — they are the same two numbers the `than_count` / `mtrs_mismatch` save guards check the grid against, so typing them was pure error surface. Qty Mtrs has **no DB column** (Σ line length; server-side default computed from the saved lines).
- **Line grid collapses** to the picked thans + one blank spare via `HideEmptyRows` on tbody `gd-line-rows` (the fixed 20-row block is gone). `DespatchAmountCalc` walks the DOM (`line_t_sr_${n}` until missing) rather than its `lineRows` prop, since a saved despatch can render more rows than the constant.

## GL posting — the delete-before-guard rule (systemic)
On EDIT, every GL-posting form must **delete old (vtype,vno) rows UNCONDITIONALLY**, then re-post only if it qualifies — otherwise editing a voucher into a non-postable state orphans stale ledger rows. Fixed in: godown (GDN), packi (GPV), yarn-sale (YSV), warped-beam (EXT), grey-despatch (GDP). Yarn-purchase (YPV) was already correct. **grey-despatch-dami posts NO GL** — it must never delete shared GDP rows (was wiping real despatch postings).
